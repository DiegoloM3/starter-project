## Compact Rules (auto-resolved into sub-agent prompts)

### When touching `frontend/lib/**` (any layer):
- Domain layer is pure Dart — NO imports from data, presentation, or any non-Dart project module (AV 2.1.1)
- Data layer imports ONLY from domain (AV 1.1.1, 1.1.2)
- Presentation imports ONLY from domain (AV 3.1.1, 3.1.2)
- core/ and shared/ allowed for cross-cutting, respecting hierarchy

### When writing data sources:
- ONLY place that touches Firebase/APIs/local storage/hardware (AV 1.2.3, 1.2.4)
- Throws exceptions — no Failure objects (AV 1.2.1)
- Pure data conversion only (AV 1.2.2)

### When writing models:
- MUST extend an Entity from `domain/entities` (AV 1.3.1)
- MUST have `EntityClass toEntity()` (AV 1.3.2)
- MUST have `factory fromRawData(...)` (AV 1.3.3)

### When writing repository implementations:
- Class name pattern: `{Interface}Impl` (AV 1.4.1)
- Returns `DataState<T>` for API calls (AV 1.4.3)
- ONLY place to import data providers (AV 1.4.4)

### When writing entities:
- No data fetching, no presentation logic (AV 2.2.1)
- Business logic only (AV 2.2.2)

### When writing use_cases:
- Single business operation per use case (AV 2.3.1)
- Implement `call` from base `UseCase<Type, Params>` in `core/usecase/usecase.dart`
- Use repository INTERFACES, not impls (AV 2.3.2)

### When writing repository interfaces:
- Abstract only — no implementation (AV 2.4.1)
- Return entities, NEVER models (AV 2.4.2)

### When writing BLoCs/cubits:
- ONLY consumer of use_cases in presentation (AV 3.2.2, 3.2.3)
- UI state management only — no business logic (AV 3.2.1)

### When writing screens:
- Delegate to BLoCs (AV 3.3.1)
- Use entities, not models (AV 3.3.2)

### When writing widgets:
- Reusable, not feature-bound (AV 3.4.1)
- Receive data via constructor or state mgmt (AV 3.4.2)

### Coding quality (always):
- CG1 Boy Scout — leave code cleaner than found
- CG2 Names: classes=nouns, functions=verbs, intention-revealing, pronounceable
- CG3 Functions: small, nesting ≤ 2, ≤ 2 args, SRP, Command-Query Separation
- CG4 TDD: write failing test first; minimal test to fail; minimal code to pass (Strict TDD Mode = ENABLED)
- CG5 Classes: small, single responsibility, few instance vars
- CG6 Use abstract classes to isolate from change

### Backend (Firestore/Storage):
- Schema location: `backend/docs/DB_SCHEMA.md` (folder must be created)
- Thumbnails go to Cloud Storage path `media/articles`, Firestore stores only the URL reference
- Rules in `backend/firestore.rules` and `backend/storage.rules`
- Test rules locally with `firebase emulators:start` before deploy

### Git/PR conventions:
- Conventional commits, no AI attribution / Co-Authored-By (per ~/.claude/CLAUDE.md)
- One PR per change, branch per change
- Boy Scout cleanups belong in the same PR as the change that prompted them
